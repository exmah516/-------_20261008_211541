# H：手柄恢复与根因核查

## 修改

- `手柄/Handle.h`定义`kHandleResumeSettleMs = 500`。重新打开、有效接收间隔严格大于1500 ms、设备会话号变化进入静置；首次连接不追加恢复延迟。
- `Handle::poll`只允许新有效采样推进静置，连续500 ms结束后，以结束样本提出一次重建请求。沿用250 ms陈旧门槛判断连续区间中断。重复缓存、无效帧或再次超过250 ms的接收间隔不能完成计时。
- 接收线程`remote_handle_bridge::put_sample`保存`continuous_since_ms`，主循环因ADS等待300 ms时也按实际接收采样的连续区间计时。无效帧中断连续区间，不刷新最后有效时间，保留第五轮缓存/断开语义。
- `main.cpp`将`resume_settling()`接入原`handle_soft_hold_active`。删除首帧立即复位的重复代码，使用已有公共恢复分支在静置结束后复位两通道滤波和四个prev缓存，再执行原基准重建。
- `motion_sync::rebase_dual_after_return`原本就刷新轴1/6的`base_rel`、`handle_ref`、`rot_ref`、`rot_base_rel`和累计目标；本轮保留这一实现，使用当前反馈和结束样本。
- 原循环末尾力反馈调用没有排除手柄保持，会覆盖入口清力。现在只增加`!handle_soft_hold_active`，静置期间轴向力、力矩均为零。
- 原`recovery_event_text`及`recovery_status`显示“导丝手柄恢复中”“导管手柄恢复中”，沿原EventText→RecoveryText到现有介入面板；未增加界面状态逻辑。U尚未实现主窗口新提示行。
- 主端DeviceEpoch→共享内存→HandleSample→HandleFrame→HMAC→数据端桥接详见[protocol.md](protocol.md)。三份协议说明均已同步。

## 五项怀疑的结论与证据

| 怀疑 | 核查结论 | 处理与证据 |
|---|---|---|
| 重建时滤波器未复位 | **未确认**。修改前main公共恢复分支已经reset线性/旋转两通道并更新四个prev缓存；motion_sync原本就重建轴1/6基准。 | 保留复位，将首帧立即恢复改为500 ms结束后恢复。结束后相同原始样本再持续500 ms，四轴完全连续，无残余滤波收敛位移。 |
| 使用旧缓存重建 | 未发现恢复路径固定拷贝断开前样本的赋值。原Handle最多保留5 s缓存，首帧即可恢复，不能保证设备后续开机运动已结束。 | 新请求必须由结束时的新有效样本触发；断言ref等于结束样本。重复缓存和invalid帧均不能完成静置；invalid不刷新时间戳。 |
| fVels未清零导致运动前馈 | 四轴位置映射不读取fVels；实际用户是force_feedback阻尼。原代码已有超过250 ms清速度，不能将本项称为已证实的位置窜动根因。 | 按要求静置中和完成poll清恢复手柄的两个速度通道。另确认“入口清力后末尾重新施力”，独立生产函数测试证明旧路径非零、新路径全零。 |
| 旋转跨圈跳变 | 映射直接使用SDK关节值，滤波为普通一阶；没有角度归一化。SDK头文件只给getJoints签名，未定义正常返回值是否在±π回卷。**无法确认正常会话跨圈是现场根因。** | 会话变化同时发生2π零点跳变已回放，旧映射产生约360°偏差，新路径无偏差。未擅自增加正常旋转unwrap；实机正常跨圈未验证。 |
| 快速宿主/SDK重开改变零点，小于1.5 s | **确认协议缺口**。旧HandleFrame没有设备会话字段，旧Handle::poll只按超过1500 ms间隔申请重建；50 ms的新SDK坐标可直接进入旧基准。 | 每次成功openDevice递增该设备epoch，监管器跨宿主重启保留计数；发现变化即静置。分别对582、587回放50 ms变化及零点跳变，旧路径跳变，新路径保持500 ms并只重建一次。 |

另外确认“首帧即跟随，后续开机机械运动仍被映射”的缺口：重新打开或1.6 s断采样后，首帧位置不变，再在400 ms内逐步移动并转动10°。旧路径跟随这段移动；新路径以静置结束位置重建，不追赶该位移。

## 回放和验收边界

`tools/revision_uhn/run_handle.py`对HEAD和当前源码分别编译。确定时钟替换Windows tick；实际生产Handle、桥接、HandleFilterState、motion_sync、plc_io::load_pos_from_actual、force_feedback参与运行；分别抽取两个版本main的恢复、保持、滤波、四轴映射表达式。硬件依赖使用原ADS mock，不连接设备。

分别对SN582、587执行四种场景：重新打开+渐进位移/10°；1.6 s间隔；50 ms会话变化+零点改变；会话变化+2π旋转零点改变。另有251 ms断采样重计时、invalid帧重计时和独立清力门控，共11个当前场景通过。HEAD的8个对应跳变场景和1个旧清力覆盖场景均确认重现。

逐10 ms断言前500 ms轴1/2/6/7探针与原值逐位相等；500 ms结束仅重建一次；同一原始值继续500 ms无漂移；之后新增小位移恢复连续跟随。见`handle/fixed/results.log`、`handle/baseline/results.log`和各自`four_axes.csv`。

四轴探针使用生产线性增量、旋转表达式和真实重建，窗口/回退约束由原有dual_control、return_recovery、round5_main完整分支回放覆盖；本测试不等同于整台机器人或实物运动。位移输入为`2 / cfg.k_handle_to_mm`，即现有映射对应2 mm的SDK增量。SDK未定义关节0物理长度单位，不能把它称作已完成“实物手柄精确位移2 mm”校准；该物理验收保留现场执行。

第五轮原有1500 ms重建门槛、250 ms陈旧速度门槛、5 s手柄断开门槛、1 s重试周期、PLC/回退恢复规则均保留。唯一新增控制时间常量是要求的500 ms。
