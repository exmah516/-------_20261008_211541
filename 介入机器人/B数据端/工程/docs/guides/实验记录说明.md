# 实验记录与力反馈

数据端 ADS.exe 启动后默认开启实验记录，无需主端点击。记录器的正常停止接口会排空写盘队列并保存元数据；当前主循环没有公共退出入口。启动失败会在控制台打印错误码；记录与运动控制、两侧力反馈开关独立。

输出相对于 ADS 的当前工作目录：records/YYYYMMDD/HHMMSS_auto/。正常入口的工作目录为 ADS 程序输出目录；同名自动追加编号，不覆盖已有记录。

- force.csv：目标100 Hz，两组传感器的原始电压、装机零点、纯净轴向力/扭矩及有效标志。力单位N，扭矩单位N·m；纯净值包含传感器和装机两层标定，不进入反馈死区、限幅、保持和手柄比例。第一组clean_force_n/clean_handle_torque_nm为导管，第二组clean_force_2_n/clean_handle_torque_2_nm为导丝。
- motion.csv：目标50 Hz，时间、位置有效性、七轴相对左端位置，以及 axis1_handle_valid（导管587）和 axis6_handle_valid（导丝582）。不记录手柄平移/转动数据；有效性取实际轮询结果。旋转轴沿用PLC原单位。
- session.json：schema_version=9，起止时间、手柄序列号、ADS通信与写盘丢样统计、结束原因。版本6起纯净值采用两层标定；旧版本5只有传感器轴向力和切向力乘3 mm的扭矩，不能直接混用。原16列顺序保持不变；版本8追加四列数据端输出和两列保持状态。

时间轴使用QPC相对微秒。运动表取ADS偶数序号；无效位置/力写NaN，未取零时仍记录原始电压，标定有效性为0。异步写盘使用有界队列；不要将缺样或NaN当成零。强制结束进程可能丢失尚未落盘的末尾数据，且不会完成最终元数据。

主端“力反馈与夹持”区域：

- **导管力反馈 / 导丝力反馈**：独立开闭，导管fn_1/ft_1→手柄587，导丝fn_2/ft_2→手柄582，与轴1/轴6的运动控制对象一致。
- **力反馈取零点**：器械空载时点击，采集当前连续3帧ADS力数据平均值；不自动开启任何一侧。尚未取零时首次开启反馈仍自动取零，之后切换开关复用已采零点。
- **开启保持 / 关闭保持**：默认开启，仅控制换手保持。触发时锁存约100 ms慢速平滑后的力和扭矩；换手/重同步完成后，对应轴向任一方向移动2 mm或等待400 ms，再用300 ms线性过渡恢复实时值。轴向力低通始终按输出有效条件启用。

数据端 control_types.h 的 ControlConfig 中：

    double force_feedback_582_force_scale = 0.3;  // 导丝582：力
    double force_feedback_582_torque_scale = 0.3; // 导丝582：扭矩
    double force_feedback_587_force_scale = 0.3;  // 导管587：力
    double force_feedback_587_torque_scale = 0.3; // 导管587：扭矩
    double force_feedback_force_filter_alpha = 0.25; // 轴向力低通

四个参数分别乘在对应手柄现有标定、增益、死区和限幅处理后的力/扭矩上，互不影响，也不叠乘旧比例。对应手柄的两项比例设为0.5时，原反馈1 N、2 N·mm变成0.5 N、1 N·mm。调整比例只需重新编译并部署数据端；独立开关、取零和保持功能仍需使用支持这些功能的主端。

阻尼已移至主端 `VI.HandleHost/Program.cs`，直接使用本周期 `getEncVel[0]`；默认系数0.01、阻尼上限±0.5 N，环境力变化率8 N/s，最终轴向力上限±1.2 N。扭矩沿用原通道。参数和现场步骤见[力反馈说明](力反馈说明.md)。

force.csv新增列依次为 `ff_582_out_f,ff_582_out_n,ff_587_out_f,ff_587_out_n,hold_582_active,hold_587_active`。前四列记录本拍数据端发送的轴向环境力（N）和扭矩（N·m），后两列为保持状态1/0（包含过渡期间）。这些输出列不包含宿主本地阻尼、变化率限制或最终限幅；纯净测量列仍独立于所有反馈策略。

相关实现：数据端 experiment_recorder.*、async_csv_writer.h、force_feedback.cpp、main.cpp；主端 VI.Module.Intervention/InterventionPanel.xaml 与 VI.Service.Robot。

## events.csv（schema 9）

每行格式为 `event_index,elapsed_us,ads_snapshot_sequence,event_code,value`。event_index 为本会话递增事件序号，elapsed_us 为事件发生时的 QPC 相对微秒，ads_snapshot_sequence 为主循环当前已消费的 ADS attempt_sequence；没有消费过快照时为 0。缺帧期间可以有多个事件引用同一个序号，该列不表示事件处拥有新的有效位置。

事件码与原因码集中定义于数据端 `experiment_events.h`。下表中 `pack(lo, hi) = lo | (hi << 16)`；按事件码解码 value，未打包的值直接读取。旧 ModeSwitch=1、SpacingRecoveryStart=2 保留原语义。

连接保持来源：1=ADS，2=587轮询失败，4=582轮询失败，8=587恢复静置，16=582恢复静置，32=初同步。多个来源可同时存在。短采样空档按保留的手柄缓存规则不会必然进入保持，不能把没有Hold事件当成没有丢包。

命令结果：0=Submitted，1=Succeeded，2=Failed，3=Unknown（结果槽不可判定），4=TimedOut，5=QueueRejected，6=ObservedAck（PLC已确认，无需再依赖Commit回执）。Submitted表示进入队列/发布输出；Succeeded来自原有通信结果或motion generation确认。它们不表示机械夹紧或NC动作已现场验收。

事件沿用异步有界队列；常态入队只复制EventCsvRow，不等待磁盘、不开文件、不执行ADS写入。新代码只观察原判定/结果，不修改控制门控或动作量。队列满仍采用原丢行机制；session.json 的 events 丢行/写错误统计用于判断时间线是否完整。取消回退的Clear在协调器reset后由一个仅记录使用的序号继续观察结果，不重新发送。

逐拍证据：`tools/refactor_baseline/run.py --events`。它先比较34个原黄金场景，再运行2个仅检查事件的输入，验证所有34个事件码、事件顺序/原因/快照序号，以及从事件重建control_active、connection_hold、planned phase、spacing phase、先行active五项逐拍状态。CSV实际序列化与schema由既有recording_feedback_test检查（示例快照序号123、456）。
