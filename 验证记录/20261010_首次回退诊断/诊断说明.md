# 首次回退后反复 ADS 快照中断

## 当前结论

现场反馈：导管与导丝一起控制，在递送/撤出界面使用导管手柄，首次触发回退时反复进入快照中断、重连与就绪流程；运行的是 Debug。尚无首次失败前的底层日志，现场故障尚未复现或修复。

对照原 `260316/64位ADS - 相对路径 - 传数组 - 加上手柄`，诊断修改前的 `ads_communication.cpp/.h`、`ADSComm.cpp`、`plc_io.cpp`、`motion_sync.cpp` 内容完全一致。main.cpp 业务差异为用户描述的触发条件拆分及 wire_caused_g 判断；control_types.h 差异为共用夹紧值 600/500 改为 1000/1000。相同源码不能排除构建模式、运行版本和现场状态差异。

`clear_runtime_connection_state()` 会清空事件缓存，其中 self_check_done 变为 false；主循环原先把此变化一律描述为“PLC 自检重新开始”。因此这条日志不能证明 PLC 真正重启或重新执行自检。

## 本次改动

仅添加诊断和修正日志描述，保持运动控制行为不变：

- ADS 失败发生时立即保存操作类型及底层错误，避免后续成功请求清掉 GetLastError。
- 首次进入保持时打印/保存快照就绪条件、通信状态、延迟、重连次数、回退阶段、腿数、轴目标及 PLC 回退错误。
- 若主线程先等满300ms、底层错误稍后返回，保持期间最多每秒补记新失败。
- 保存到实际 ADS.exe 旁的 `ads_fault_diagnostics.log`，启动时打印 `[ADS-DIAG] build=Debug/Release` 和编译时间。
- 区分断线导致的自检缓存失效与在线自检完成标志下降。停止当前控制的行为不变。

没有回滚两处双手柄触发逻辑，没有改变电缸1000预设、超时阈值、保护或PLC工程。修改前源码在“修改前”子目录。

## 离线验证

`B_从端电脑/工程/ADS项目/tools/run_ads_diagnostics_test.py` 编译真实通信服务和替代 CADSComm，不链接 ADS DLL，不运行完整 ADS.exe，不连接硬件。

22项通过：双腿 Prepare/Commit 数据下发、队列子项错误与核心拍区分、心跳写失败、读超时、写超时、未知 Commit 保留双轴 possibly_started 标志、成功请求与断线清理后仍保留诊断、PLC周期停滞、时间倒退、非有限位置以及自检缓存清空。结果见 offline-tests.log。这些是故障注入验证，不是现场根因复现。

## 现场需要的证据

1. 从新“工程/ADS项目/ADS.sln”重新构建。确认从端电脑使用本次修改后的工程/程序，且没有另一个 ADS.exe。
2. 在台架允许的条件下按原操作观察一次；不要在回退中打断点或单步。出现首次中断后按原流程停止，不必持续推动重复触发。
3. 取实际运行 EXE 旁的 `ads_fault_diagnostics.log`：Debug 位于 `工程/ADS项目/x64/Debug`，Release 位于 `工程/ADS项目/x64/Release`。提供第一次故障附近的 `[ADS-DIAG]` 记录及此前控制台输出。
4. 如需区分调试器影响，保持同一 Debug 构建，用 Ctrl+F5 启动；Release 是另一个变量，应单独比较，不同时更改夹紧参数或回退逻辑。

日志中的 `SUM_READ`、`SUM_WRITE`、`PLC_TASK_STALLED`、`PLC_TIME_REGRESSED` 或就绪标志用于确定下一步。现阶段不把 Debug 认定为原因，也不依据“重新自检”文字回滚运动逻辑。
